## Project Summary

Bramble is an opinionated retrospective tool for engineering teams at Series A–C startups. It owns the hand-off between meeting and follow-through: every action gets an owner before the meeting ends and carries forward into the next retro until it's closed. Register is hybrid, leaning product — the in-app surface earns familiarity; the marketing surface does the brand work.

## Product context

- **Register**: hybrid, leaning product.
- **Primary user**: engineering managers at 20–200-person startups, running biweekly retros.
- **Jobs-to-be-done**: capture before the meeting; cluster + vote + decide during; walk out with owned actions; carry open items forward.
- **Personality (3 words)**: candid, structured, low-key.
- **Top anti-references**: EasyRetro (no opinion), Confluence template (a blank page), Miro (45-minute setup tax), Notion (database tool dressed as a meeting tool), Slack standup bots (async messaging is not facilitation).

## UX laws

<!-- Synthesized from DESIGN.md UX foundation. UX is the constraint — everything in `## Design laws` below must serve these. When UX and UI conflict, UX wins. -->

These come first. UI choices below must serve these UX commitments — when they conflict, UX wins.

- Recognition over recall — owners are picked from a populated list, never typed.
- Undo over confirm — deletes show a 5-second undo toast; no "are you sure" modals.
- Keyboard-first facilitation — every meeting action has a single-key shortcut; the meeting can be run end-to-end without a mouse, including via screen reader.
- Progressive disclosure — settings collapse until needed; patterns view hidden until the team has ≥6 retros.
- System speaks the user's language — "carryover", "actions", "owners". Never "tickets", "tasks", "stickies", "kudos".
- Top flows: pre-meeting writing (Slack DM → writing surface), running the meeting (cluster → vote → assign owners), post-meeting follow-through (carryover into next retro).
- Accessibility: WCAG 2.1 AA throughout; `prefers-reduced-motion` respected on every surface; keyboard-only facilitation must work end-to-end.

## Design laws

<!-- Synthesized from DESIGN.md UI system. These execute the UX laws above. -->

These execute the UX laws above. If a design choice would undermine a UX law, it loses.

- **Color**: Restrained strategy. OKLCH only — no `#000`, no `#FFF`. One accent (deep evergreen `oklch(38% 0.10 155)`) on ≤8% of surface, reserved for live-meeting state and primary actions.
- **Type**: Source Serif 4 (display) + Inter (body) + JetBrains Mono (integrations only). Base 16px, scale 1.25, body line-height 1.55, measure cap 68ch on prose / 56ch in cards.
- **Spacing**: 4 8 12 16 24 32 48 64 96 px scale. Left-anchored 720px reading column with 280px sidebar; no grid in-app.
- **Motion**: expo-out easing, durations 120/220/380ms. Single signature transition: card reveal at meeting start. Never animate layout properties, never use bounce, never spring. Degrades to instant under reduced-motion.
- **Cards**: allowed only on the writing and meeting surfaces. Lists use hairline borders, not card stacks.
- **Components**: 10 primitives — Button (square 2px corners, no shadow at rest), Input (bottom border only, accent on focus), Tag (border + label, never color-only), Modal (used in only two flows in the entire product), and so on.

## Code conventions

<!-- Synthesized from CODE.md. -->

- **Stack**: Remix on Node 20, Postgres 16 + Drizzle, Auth.js, Fly.io single region, LiveKit data-channels for real-time meeting state. No animation library, no GraphQL, no tRPC.
- **Tooling**: TypeScript 5.4 `strict: true`, pnpm 9, Biome (no Prettier, no ESLint), Vitest, Playwright. Migrations forward-only via Drizzle Kit.
- **Architecture**: single Remix app. State preference order: URL → DB → component-local. Domain modules under `app/lib/<domain>/{model,queries,commands,service}.ts`; routes import from `service.ts` only.
- **Naming**: `kebab-case.ts` files, `PascalCase.tsx` components, one component per file, default-export the component. Imports absolute from `~/`.
- **Comments**: explain *why*, never *what*. If a comment names what the code does, rename the code.
- **Errors**: propagate. Catch only at route boundaries (rendering an error UI) or when translating an external error into a domain one.
- **Performance budgets** (hard, build-fails): LCP ≤1.5s on writing surface / ≤2.0s elsewhere; INP ≤200ms in meeting surface (vote ≤80ms); CLS ≤0.05; initial JS ≤80kb gzip per route (110kb on the meeting surface for LiveKit).
- **Security baselines**: Auth.js with Postgres-backed sessions; Zod validation at route boundaries; strict CSP with nonces (no `unsafe-inline`); secrets via Fly only; `pnpm audit` blocks on `high+`.

## Anti-patterns (always reject)

The following are non-negotiable bans. If the user asks for them anyway, push back once with a concrete alternative; if they insist, comply but flag the trade-off.

### Product

- Vague personas ("developers who want better tools") — name role, seniority, company stage, what they tried last.
- Generic positioning ("the all-in-one platform for modern teams") — anchor on the specific job at the specific moment.
- Education framing for an aware audience — solve the problem, don't teach it.
- Hedging language in brand voice — "might", "could", "consider", "perhaps".
- Feature lists as positioning — lead with the promise, not the bullet list.
- Ornamental success metrics ("increased engagement") — use real ones (retention, completion rate, time-to-first-value).
- Anti-references that aren't real — name actual products to avoid, not abstract qualities.
- Brand personality as three buzzwords ("modern, clean, friendly") — be specific enough to recognize unsigned.

### UX

- Confirm-instead-of-undo — default to undo; reserve confirm for irreversible actions.
- Modal-first thinking — most modals want to be inline panels, routes, or side sheets.
- Hidden state — every loading, success, and error must show.
- Empty states that aren't empty states — they're the cheapest onboarding surface.
- Generic error messages — name what failed, why, and what to do next.
- Inconsistent validation — pick blur or submit; let users fix one error at a time.
- Click targets <44×44 on mobile.
- Dark patterns — pre-checked opt-ins, sneak-into-cart, roach-motel cancellation, confirm-shaming.
- Lossy navigation — back/refresh/URL must reflect screen state.
- Accessibility as cleanup — keyboard + focus visibility belong in v1 of every component.
- Onboarding as a tour — show value on the first screen, not in a modal carousel.
- Recall over recognition — remind, don't make the user remember.

### Design

- Purple gradients on dark backgrounds; pure black/white on body surfaces; neon-on-black; gradient text; gray text on colored backgrounds.
- More than one decisive accent.
- System-default-only type stacks; tight body line-height (<1.4); measure >75ch; flat scale (<1.2); all-caps headlines >4 words.
- Nested cards; identical-card grids; hero-metric template; side-stripe borders; default drop shadows; default glassmorphism.
- Bounce easing; animation on layout properties; ignoring `prefers-reduced-motion`; "delight" animations on critical paths.
- Composition tells: icon-headline-paragraph card grids; three-column "How it works"; "trusted by" logo strips at 40%; tilted-product-screenshot-with-glow.

### Code

- Premature abstraction — three similar lines is not a pattern.
- Half-finished implementations, TODO branches, unused fallback paths.
- Defensive validation on internal inputs already guaranteed by types.
- Comments restating what the code does — rename instead.
- Dead code "kept in case" — version control remembers.
- Backward-compat shims for code you own — change the callers.
- Catch-and-rethrow-with-worse-message; empty catches; `null` where an exception belongs.
- Booleans modeling a state machine — use a discriminated union or XState.
- Tests that mock everything and assert call shape; snapshot tests as primary signal.
- `utils.ts` / `helpers.ts` collections — group by domain.
- `as any` / `// @ts-expect-error` without a `// reason:` comment.
- Magic timing (`setTimeout` to fix a race) — model the state transition explicitly.
- Bypassing safety: `--no-verify`, `--force`, disabled lint rules — the check is usually right.

## AI Slop self-check

Before showing any UI to the user, run this check:

- [ ] Does this look like a stranger could tell an AI made it? If yes, redesign.
- [ ] Are the color choices a category reflex (purple-for-AI, neon-for-crypto, blue-for-banking)? If yes, reconsider.
- [ ] Is every element earning its place, or is there ornament-for-ornament's-sake?
- [ ] Did I default to a hero-metric layout, identical-card grid, or modal-first thinking? If yes, see `DESIGN.md` for the chosen pattern.
- [ ] Does the copy hedge ("might", "could", "consider") instead of taking a stance?

## When to ask the user

- The request contradicts one of the briefs.
- The request requires a decision the briefs don't cover (new section, new flow, new dependency).
- The request would cross a performance / security / accessibility line in `CODE.md` or `DESIGN.md`.
- You are about to take a destructive or hard-to-reverse action.
