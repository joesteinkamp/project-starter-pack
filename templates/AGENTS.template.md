## Workflow expectations

Before any non-trivial change, read the three briefs at the project root:

1. **`PRODUCT.md`** — who this is for, why it exists, brand stance.
2. **`DESIGN.md`** — UX foundation (users, IA, flows, success metrics) **and** UI system (color, type, spacing, motion, components). Tokens live in the YAML front matter; rationale lives in the markdown body.
3. **`CODE.md`** — stack, architecture, conventions, performance, security.
4. **`PROJECT.md`** *(if present)* — the active initiative's goal, non-goals, and scope slice. Treat its non-goals as hard limits; if a request would expand scope beyond what's listed, surface that to the user before acting.

If a request is ambiguous, ask before assuming. Do not invent product context, design tokens, or stack decisions that contradict these briefs.

## Always-on rules

### Git discipline

- Work on feature branches; never commit to `main`/`master`.
- Branch names use `<type>/<description>` (e.g., `feat/user-search`, `fix/login-redirect`).
- Imperative-mood commits, ≤72 char subject, single logical change per commit.
- Never force-push shared branches. Never commit secrets.

### Security

- Validate all external input. Redact secrets from logs.
- Use parameterized queries for SQL. Avoid `eval`, `exec`, dynamic imports of untrusted strings.
- Pin dependencies; audit before adding them.
- Read secrets from environment variables only — never hard-code.

### Testing

- Test behavior and public contracts, not implementation details.
- Run the relevant test suite before declaring work complete.
- Don't weaken tests to inflate coverage metrics.
- Mock external dependencies for deterministic execution.

## AI slop self-check

Before showing any UI to the user, run this check:

- [ ] Does this look like a stranger could tell an AI made it? If yes, redesign.
- [ ] Are the color choices a category reflex (purple-for-AI, neon-for-crypto, blue-for-banking)? If yes, reconsider.
- [ ] Is every element earning its place, or is there ornament-for-ornament's-sake?
- [ ] Did I default to a hero-metric layout, identical-card grid, or modal-first thinking? If yes, see `DESIGN.md` for the chosen pattern.
- [ ] Does the copy hedge ("might", "could", "consider") instead of taking a stance?

## When to ask the user

- The request contradicts one of the briefs.
- The request requires a decision the briefs don't cover (new section, new flow, new dependency).
- The request would cross a performance / security / accessibility line in `CODE.md` or `DESIGN.md`.
- You are about to take a destructive or hard-to-reverse action.

## Project-specific rules and skills

Extensions live under `.agents/`:

- `.agents/rules/*.md` — glob-scoped passive constraints. Frontmatter: `description` (one-line summary), `globs` (file patterns where the rule activates), `alwaysApply` (reserve `true` for rare project-wide concerns).
- `.agents/rules/optional/*.md` — opt-in rules for specific frameworks/stacks.
- `.agents/skills/*.md` — named workflows users invoke actively. Frontmatter: `description`, `trigger` (the natural-language phrase that invokes it), `risk` (`low` | `medium` | `high`).

Filenames use lowercase with hyphens (e.g., `commit-push-merge.md`). Lead with the rule statement; bury rationale later. One concept per file.

If `.agents/` does not exist yet, create it lazily when the first project-specific rule or skill is added.
