# Agent Instructions

> Entry point for any AI coding agent working in **this** repository — the `project-starter-pack`
> source, not a project generated by it. Follows the [agents.md](https://agents.md) convention, so
> Codex, Cursor, Antigravity, and Copilot read it automatically; Claude Code reaches it through
> `CLAUDE.md`.

> **Layering:** This is the **project / codebase** layer — rules true of *this repository*. It
> omits user/global concerns (tool preferences, autonomy level, memory strategy, output
> conventions), which live in the operator's own global instructions. The two layers compose;
> where they conflict for work in this repo, the project layer wins.

## What this repo is

A portable AI project starter. It walks a designer through a Product, Design (UX + UI, plus the
`WRITING.md` rules), and Technical brief, then wires up an `AGENTS.md` **router** in the target
project. It runs in Claude Code, Codex, Cursor, and Antigravity — same flows, same outputs.

There are no `PRODUCT.md` / `DESIGN.md` / `CODE.md` briefs here. This repo is the generator; those
files are its *output*. `examples/saga-reader/` is the worked render that shows what it produces.

## Before you change anything

`./test.sh` is the gate. It needs only `bash`, `grep`, `sed`, and `jq`, runs in seconds, and must
be green before any commit. It enforces contracts that rot silently otherwise:

- **Slot ↔ question ↔ skill ↔ template.** Every `{{SLOT}}` a template defines has a question (or
  a default) that feeds it and a skill that fills it. Add a slot without its question and the
  pack stays "working" while the output has a hole.
- **The portability contract.** Skills are the engine; every flow must exist as a skill, because
  Codex has no command surface and Antigravity has neither. Harness-specific tool names
  (`AskUserQuestion`, the `Write` tool, `$ARGUMENTS`, Claude's shell-injection dialect, "plugin
  root") are **banned** in `skills/`, `questionnaires/`, `conventions/`, and `guardrails/`.
  `conventions/question-mechanics.md` is the single exempt file — naming harness tools there is
  what keeps them out of everywhere else.
- **Guardrail wiring.** Every anti-pattern registry is embedded by the brief that owns it, so
  reading a brief is also reading its bans.
- **The example is a fixture.** `examples/saga-reader/` must be a complete, placeholder-free
  render whose structure matches the templates. Change a template heading, re-render the example.

## Conventions that are easy to break

- **Skills are the source of truth. Commands are thin wrappers** — under 12 non-blank lines,
  whose only job is "invoke the `<name>` skill". Flow logic in a command is a second source of
  truth that only Claude and Cursor ever read.
- **The command surface is three verbs:** `setup`, `extract`, `validate` — generate, seed, check.
  The three brief flows are skills only, reached through `setup`'s scope word or by name. Don't
  add a command for a flow without a reason that survives "is this a verb, or a namespace?".
- **Never hand-edit `commands/cursor/`.** It is generated from `commands/*.md` by
  `render-ports.sh`, which `install.sh` runs on every install. Edit the canonical command and
  re-render. The ports are gitignored.
- **Skills resolve resources with `../../`**, never a bare `templates/…`. Installation symlinks
  each skill dir alone into a tool's skills folder; only the relative path resolves back into the
  checkout.
- **`/starter:` is Claude's syntax.** It may appear only in files describing a Claude surface.
  Elsewhere, name the flow (`design-brief`) — the invocation differs per tool.
- **Don't reintroduce synthesis.** The generated `AGENTS.md` is a router carrying no brief
  content, which is why it never goes stale. Anything that copies brief content into it is a
  drift machine — that is why the orchestrator flow was deleted.

## Change Log

`CHANGELOG.md` records AI-made changes as **decisions, not diffs**. Each entry captures what
changed, the ask that prompted it, why this approach, and what was considered and rejected. When
a change supersedes an earlier entry, name it and say what new information changed the call.

Propose the entry and get explicit approval before writing it. Never commit it unasked.

## Project knowledge

Read `memory/knowledge.md` before substantive work — non-obvious facts and gotchas the code
alone won't tell you.

When a conversation required *discovery* — the first answer was wrong, missed context, or only
came right after back-and-forth — ask whether it belongs in `memory/knowledge.md`. The trigger is
surprise, not chat volume; never save automatically. When you edit a governing doc (this file,
`CLAUDE.md`, either `memory/` file), append a dated entry to `memory/changelog.md` saying what
changed and why. One line is fine — the audit value is the date plus the reason.

## When to ask the user

- A change would grow the command surface, or add a slot, question, or guardrail.
- `./test.sh` would need relaxing to make a change pass. Retarget a check; don't delete it.
- A change would make one tool's experience diverge from the others'.
- You are about to take a destructive or hard-to-reverse action.
